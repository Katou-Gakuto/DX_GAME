## 結論（かなり有力）

👉 **DxLib終了前後で「画像・音・モデルなどのリソース解放タイミング」が壊れている可能性が高いです**

特にこのログ：

```cpp
D3DKMT_DESTROYALLOCATION2
```

は
👉 **GPUリソース（テクスチャなど）破棄中のクラッシュ**
なので、

> 「すでに解放済みのリソースに触っている」
> or
> 「DxLib終了後に描画系APIを呼んでいる」

のどちらかが本命です。

---

## DxLibでよくある地雷パターン

### ❌ ① `DxLib_End()`の後に何かしてる

```cpp
DxLib_End();

// これやるとアウト
DrawGraph(...);
DeleteGraph(...);
```

👉 **DxLib_End()後は一切DxLib関数を呼んではダメ**

---

### ❌ ② グローバル変数のデストラクタ問題（超多い）

```cpp
class Texture {
    int handle;
    ~Texture() {
        DeleteGraph(handle);  // ← これ危険
    }
};

Texture g_tex; // グローバル
```

👉 プログラム終了時：

1. `DxLib_End()` が先に呼ばれる
2. その後 `g_tex` のデストラクタが走る
3. `DeleteGraph` 実行 → 💥クラッシュ

---

### ❌ ③ 二重解放

```cpp
DeleteGraph(handle);
DeleteGraph(handle); // ← これ
```

---

### ❌ ④ 解放忘れ＋DxLib側に任せてるが…

基本はOKですが、
自作ラッパーと混ざると壊れやすいです。

---

## 安全な終了パターン（これに寄せる）

### ✔ パターン1：明示的に全部解放

```cpp
// 自分のリソース解放
DeleteGraph(handle);
DeleteSoundMem(sound);

// 最後に
DxLib_End();
```

---

### ✔ パターン2：クラスに明示的な終了関数を持たせる

```cpp
class Texture {
public:
    int handle;

    void Release() {
        if (handle != -1) {
            DeleteGraph(handle);
            handle = -1;
        }
    }
};
```

```cpp
g_tex.Release();
DxLib_End();
```

👉 **デストラクタではなく手動管理が安全**

---

### ✔ パターン3：終了順を制御

```cpp
Init();
MainLoop();
Cleanup();  // ← ここで全部解放
DxLib_End();
```

---

## 切り分けチェック（これやると原因ほぼ確定）

### ① `DxLib_End()`をコメントアウト

```cpp
// DxLib_End();
```

👉 クラッシュ消えるなら
→ **終了処理まわり確定**

---

### ② Delete系を全部コメントアウト

👉 落ちなくなるなら
→ **二重解放 or 順序バグ**

---

### ③ グローバルオブジェクトを疑う

* `static`
* グローバル変数
* シングルトン

👉 ほぼ犯人はここにいます

---

## かなり重要なポイント

DxLibは内部でDirectX（= `d3d11.dll`）を使っています。

なので：

> **DxLibの使い方ミス → DirectXクラッシュに見える**

これは正常な挙動です（分かりにくいだけ）。

## まとめ

今回の症状はほぼこれ：

👉 **「DxLib終了後にGPUリソースを触ってる」**

優先的に疑うべきは：

1. グローバルオブジェクトのデストラクタ
2. Delete系の順序
3. 二重解放
